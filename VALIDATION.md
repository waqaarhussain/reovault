# Validation, 24 October 2026

Eighteen automated tests passed for this build.

The tests exercise individual recording switches; newly added cameras remaining off; restart persistence; one-time migration of the old global switch; real H.264/H.265 fragments and original-codec exports; recording rotation preserving saved clips; ONVIF-derived names; protected local control requests; date formats including `0757pm - 08:10pm`; DST repeated/nonexistent times; camera packet reference timestamps; waiting for verified timestamps before archiving; timeline grouping and gaps; authentication; credential handling; pinned-commit downloads; interactive bootstrap input; code activation and failed-start rollback.

A local MediaMTX RTSP test with synthetic video passed using the actual capture subprocess and PyAV 17.1.0. The stream supplied RTCP sender references. The engine started live view without archiving, indexed footage using those references after enabling that camera, and stopped archiving while keeping live view online. The compatible live-preview test also passed and published camera-mapped timestamps for its delayed preview.

Chromium checks passed for sign-in, live video, recorded playback, hourly versus half-hour grouping, the camera form, no JavaScript errors and no horizontal overflow on a 390-pixel mobile viewport. Source timestamps and clip exports were tested using generated video; the fixture is not real security footage and is not included in the repository.

All runtime requirements resolved to Python 3.10-compatible wheels for Ubuntu 22.04's interpreter, including PyAV 17.1.0. The development runtime itself was Python 3.12, rather than a complete Ubuntu 22.04 VM. Shell syntax, JavaScript syntax, Python compilation and Git whitespace checks passed.

Still to verify after installation: actual Reolink firmware RTCP sender-reference availability, standalone camera ONVIF names, the camera's configured clock/overlay timezone, DDNS and port forwarding, sustained 4K throughput, target-device HEVC playback, SFTP permissions for the actual Termius login, and systemd installation on the user's VPS.

If a real device provides no verified capture reference, this build intentionally waits before archiving rather than substituting server arrival time. Original-codec exports use camera keyframes and can extend slightly beyond requested edges; frame-exact arbitrary trimming is not promised. An incorrectly set camera clock or overlay timezone is reported/read as supplied, not silently changed.

Mode/hourly update: the suite now also covers mode selection and recording-state preservation, storage-only live access rejection, whole-hour file rotation, byte-bounded fragment playback/downloads, reconnect session files, visible outage gaps, crash-tail truncation and repeated supervisor retries until a camera becomes available. Physical camera reconnection and actual VPS behavior still require on-site validation.

A running local RTSP outage test passed for this update: storage-only left a disabled camera disconnected, then recorded original packets without starting its enabled compatible converter; terminating and restarting the RTSP publisher triggered automatic retry and a new recording session/file without running record again. Both resulting hourly MP4s decoded with FFmpeg. Switching to live-only stopped archive growth, and switching back to storage resumed the previously enabled camera. This is a synthetic local source, not a physical Reolink or a home internet outage.

Installer permission fix: reproduced rsync inheriting a private source directory mode (0700) and private code file mode (0600), which excludes the service user. The installer now explicitly copies code directories as 0755 and code files as 0644, restoring shell entry points to 0755 after copying. Deployment regression fixtures now use those private source permissions and verify readable/traversable release code. Package installation also waits up to 600 seconds for the dpkg lock. These checks do not run a real systemd service; the VPS startup health check remains the final check.

Python 3.10 timestamp fix: reproduced rejection of FFmpeg compact timezone offsets (+0000) using CPython 3.10’s own `_parse_isoformat_time` implementation; the colon form (+00:00) succeeds. Playlist parsing now normalizes terminal compact offsets before calling fromisoformat. Five regression cases cover positive/negative compact offsets, colon offsets and Z under a strict Python 3.10-style parser. Structural diagnostics are tested not to leak URL credentials or exception messages. All 27 tests pass in the development interpreter. This is not a full Ubuntu 22.04 runtime/systemd test.

Mux diagnostics update: error-level FFmpeg logs are captured only around each packet write and converted to fixed reason labels. Raw log strings are not persisted. Failures now include stream type, codec, packet timestamps, prior DTS, time base and observed producer-reference flags. A real AAC stream with deliberately regressing DTS reproduces ArgumentError and is classified as non-monotonic-timestamps. Generated HEVC/AAC capture passed. The physical camera’s mux cause and absent source clock are still unconfirmed; this update adds diagnostics rather than claiming to fix them.

AAC timestamp repair: user diagnostics confirmed duplicate AAC DTS with valid camera RTCP references. The guard validates AAC timestamps in the output sample clock, moves small non-increasing timestamps to the next tick, and refuses corrections larger than a quarter-second. It does not alter video timestamps or encoded packet payloads. Tests reproduce duplicate/backward AAC timestamps, verify encoded AAC payload identity, decode the repaired result, leave HEVC video timestamps unchanged and reject a large jump. Actual capture tests inject duplicate AAC timestamps into H.264/AAC and HEVC/AAC inputs and decode the resulting fragmented MP4s. All 34 tests pass locally; the physical camera still needs the user’s post-update check.
